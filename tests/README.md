# เทสต์

## วิธีรัน

เปิดเซิร์ฟเวอร์ในโฟลเดอร์โปรเจกต์แล้วเปิดหน้า `tests/run.html`

```bash
npx --yes serve -l 8845 .
```

แล้วเปิด <http://localhost:8845/tests/run.html> — ผลขึ้นเป็นรายข้อ ผ่านเป็น ✔ ไม่ผ่านเป็น ✕ พร้อมบอกว่าคาดหวังอะไรและได้อะไรมา จำนวนรวมอยู่มุมขวาบนและอยู่บนชื่อแท็บด้วย

เปิดจากไฟล์ตรงๆ (`file://`) ไม่ได้ เพราะเบราว์เซอร์ห้ามอ่านข้ามเฟรม ต้องผ่านเซิร์ฟเวอร์

`tests/` อยู่ใน `.assetsignore` — ไม่ถูกอัปขึ้นเว็บจริง

## ทำงานยังไง

แอปทั้งตัวคือ `index.html` ไฟล์เดียว ฟังก์ชันเกาะอยู่บน `window` ไม่มีโมดูลให้ import ตัวรันจึงโหลด `index.html` ใส่ iframe แล้วเรียกฟังก์ชันจริงในนั้น

สิ่งที่ถูกแทนที่คือ `sb` (ตัวเชื่อม Supabase) ของปลอมใน `harness.js` เลียนหน้าตาการเรียกแบบเดิม แต่:

- **บันทึกทุกการเขียน** — เทสต์ตรวจได้ว่า insert/update/delete ส่งอะไรไป โดยไม่มีแถวไหนขยับจริง
- **ตอบการอ่าน** ตามที่เทสต์วางไว้ล่วงหน้า
- **ใช้รหัส error จริงของ PostgREST** (`PGRST205` ตารางหาย, `PGRST202` ฟังก์ชันหาย, `42501` RLS ปฏิเสธ) เพราะโค้ดหลายจุดแยกสามอย่างนี้ออกจากกัน

**ไม่มีเทสต์ไหนแตะฐานข้อมูลจริง**

## ไม่ครอบคลุมอะไร (และทำไม)

ที่ขอมาคือ "ทุก function" — ตรงๆ คือทำไม่ได้และไม่ควรทำ ในไฟล์มีฟังก์ชันบน `window` ประมาณ 200 ตัว ส่วนใหญ่เป็นตัวเปิด/ปิดโมดัล ตัววาด HTML จากข้อมูลที่ดึงมา หรือตัวเรียก API ตรงๆ เทสต์ที่เขียนได้กับพวกนี้จะเป็นแค่ "เรียกแล้วไม่ throw" ซึ่งผ่านตลอดแม้โค้ดจะผิด — เทสต์แบบนั้นแย่กว่าไม่มี เพราะทำให้ตัวเลข coverage สวยแล้วเชื่อผิด

ที่เลือกเขียนคือส่วนที่ **ตัดสินถูก-ผิดได้จริง**: รูปร่างของสิ่งที่จะถูกเขียนลงฐานข้อมูล, สถานะที่ปุ่มควรอยู่, ลำดับที่รายการควรออกมา, และเงื่อนไขที่ตัดสินว่าใครเห็นอะไรได้

สิ่งที่ยัง**ไม่**ครอบคลุม:

- **RLS policy** — เทสต์ที่นี่ตรวจว่าฝั่งหน้าเว็บส่งอะไรไป ไม่ได้ตรวจว่าฐานข้อมูลปฏิเสธจริงไหม ตัว policy ต้องทดสอบด้วยการยิงจริงตอนล็อกอินสองบัญชี (เคยยิงมือเช็คแล้วว่า anon insert โดนปฏิเสธด้วย `42501`)
- **Supabase Auth** — สมัคร/เข้าสู่ระบบ/OAuth ใช้ session จริง ปลอมแล้วไม่ได้ทดสอบอะไร
- **การอัปโหลดไฟล์และการบีบรูป** — `kxImageFile` ใช้ canvas จริงและ HEIC ที่ Safari เท่านั้นที่ถอดได้
- **หน้าตา** — ระยะ สี ฟอนต์ ไม่มีเทสต์ ต้องดูด้วยตาหรือเทียบภาพ (มีวัดความกว้างบ้างเฉพาะที่ layout เป็นตัวตัดสินถูกผิด เช่น การ์ดสองคอลัมน์)
- **แชท** — พึ่ง poll ทุก 6 วินาทีและ session จริง

## เพิ่มเทสต์

เขียนใน `suite.js` ตามรูปแบบเดิม `w` คือ window ของแอป

```js
describe('ชื่อกลุ่ม', function () {
  it('ประโยคที่บอกว่าอะไรควรจริง', async function (w) {
    var sb = plan(w, { ตาราง: { _: { data: [...], error: null } } });
    signIn(w);
    await w.ฟังก์ชันที่จะทดสอบ();
    restore(w);
    expect(sb._writes[0].op).toBe('insert', 'เหตุผลที่ต้องเป็นแบบนี้');
  });
});
```

ข้อความที่สามใน `expect` คือเหตุผล — จะโผล่ตอนเทสต์ล้ม ทำให้คนอ่านรู้ว่าทำไมถึงเขียนไว้แบบนั้น ไม่ใช่แค่ว่ามันไม่ตรง

**เช็คว่าเทสต์มีฟันจริง**: ลองทำให้โค้ดพังแล้วดูว่าเทสต์ล้มไหม ถ้าพังแล้วยังผ่าน แปลว่าเทสต์นั้นไม่ได้ตรวจอะไร ตอนเขียนชุดนี้ลองแล้วสามจุด — ปิด `kxTableMissing` ล้ม 3 ข้อ, ปิด `kxRankFeed` ล้ม 5 ข้อ, ให้ `kxToggleConnect` เขียนผิดแบบ ล้ม 6 ข้อ
